# Decision register

61 decisions taken while building SIRE, with the reasoning that produced
them. The reasoning is the expensive part to reconstruct — a decision without its
why gets reversed by the next person who finds it inconvenient.

| Status | Meaning |
|---|---|
| **ACTIVE** | Holds today. Changing it is a deliberate act. |
| **SUPERSEDED** | Replaced by a later decision; kept so the replacement makes sense. |
| **NOT APPLICABLE** | The situation it addressed no longer exists. |

---

## The one to protect

**D1 — the Helpdesk boundary.** The decision most likely to erode, because every
erosion is individually reasonable: a public form here, an email intake there, a
customer-facing SLA because someone asked.

> Someone asking us to **do** something for them → **Helpdesk ticket**
> Someone recording that something **broke** → **SIRE case**

A ticket reading "add a public issue widget to SIRE" or "let customers see their
SIRE case" is not a feature request. It is a proposal to reopen D1, and should be
answered as one.

## The risk column

Refers to the ten integration risks from the original discovery review:

| | |
|---|---|
| **R1** | Tenant scoping is opt-in — one missing `forTenant()` leaks every tenant’s data |
| **R4** | Ticket functionality already exists — a second one splits the customer’s view |
| **R6** | Approvals are already forked five ways; a sixth is the default outcome |
| **R9** | Tests run SQLite, production is MySQL, and the gap has broken deploys |
| **R10** | No shared index strategy, no search, and a database shared by two deployments |
